1. The big picture

What "C#" and ".NET" actually are, and how your project is laid out.

C#

The language — the syntax you type. Like JavaScript is a language.

.NET

The platform — the runtime that executes your compiled code + a huge standard library (like Node.js + npm's std lib rolled together).

Compiled

Unlike JS, C# is compiled first: dotnet build turns your .cs files into a .dll the runtime runs. Errors are caught before the app starts.

Strongly typed

Every value has a declared type (int, string, PeptidePlan). The compiler rejects mismatches — this is the safety net React/JS didn't give you for free.

How your solution is organized

A solution (.sln) is a bag of projects. Each project (.csproj) compiles to one .dll. Yours has three:

Shots.sln                       ← the solution (glue)
├─ src/Shots.Domain          ← pure logic: no web, no database. Just math + models.
│     PeptidePlan, DoseTier, PlannerCalculator…
├─ src/Shots.Web             ← the ASP.NET app: API endpoints, Blazor UI, SQLite
│     Program.cs, Api/, Services/, Components/
└─ tests/Shots.Domain.Tests  ← unit tests for the Domain project

Why split them? Shots.Domain knows nothing about the web or database — you could reuse it in a console app or a phone app. This separation ("domain logic" vs "delivery mechanism") is exactly the kind of design decision interviewers love to hear you explain.

Two words you'll see on every file: namespace and using

src/Shots.Domain/Models.cs
using System.Text.Json.Serialization;   // import — "I want to use things from this box"

namespace Shots.Domain;               // this file's stuff lives in the "Shots.Domain" box

A namespace is just a folder-like label that groups related types so names don't collide. using X; at the top means "let me refer to things in box X by their short name." That's it.

2. Object vs Class vs Method vs Function ★

This is the one that trips everyone up. Let's kill the confusion for good.

Here's the single sentence to memorize:

A class is a blueprint. An object is a real thing built from that blueprint. A method is a function that belongs to a class/object. A function is just "a reusable block of code that takes inputs and gives an output."

First — clearing up "plan" vs "PeptidePlan", since they appear all over §2–4:

You'll see…What it is
PeptidePlan (Capitalized)the class — the blueprint.
plan (lowercase)an object — one specific plan built from that class.
plan.Tiers.Add(…)a method — an action you call on that object.

That capitalization is a real, reliable C# convention, not just my styling: types (classes) are PascalCase (PeptidePlan, DoseTier), and variables holding objects are camelCase (plan, tier). So the moment you see a lowercase name with a dot after it, you're looking at an object — a real thing you can poke — not a blueprint. plan is literally what you'd get from var plan = new PeptidePlan();.

Pick an analogy that clicks for you:

TermCookie analogyIn your app

object (a.k.a. instance)An actual cookie you stamped out. You can make many, each different (sprinkles, size).The specific plan "NAD+, 500mg, starts July 6" sitting in your list.
methodSomething a cookie can do to itself — "frost me."plan.Tiers.Add(tier) — a method that adds a tier to that plan.

See all four in one real snippet

src/Shots.Domain/Models.cs  +  a caller
// 1) CLASS — the blueprint. Note: it defines a shape, it is not itself "a plan".
public sealed class DoseTier
{
    public string Type { get; set; } = TierTypes.Dose;
    public double DoseMg { get; set; } = 100;
}

// 2) OBJECT — `new DoseTier{…}` builds one real instance from the blueprint.
var tier = new DoseTier { DoseMg = 150 };

// 3) METHOD — `.Add(...)` belongs to the List object `plan.Tiers`. Called WITH the dot.
plan.Tiers.Add(tier);

// 4) FUNCTION — a static helper. Give it inputs, get an output. No object needed.
//    (`plan` here is an OBJECT — assume `var plan = new PeptidePlan();` earlier.)
double days = PlannerCalculator.IntervalDays(plan);
In plain English "Stamp out a new tier and set its dose to 150. Attach that tier onto this plan. Then, separately, ask the calculator toolbox: given this plan, how many days between shots? — and remember the number."

The honest truth: in C#, "method" and "function" mean almost the same thing — a named block of code that takes inputs and returns an output. C# people just say method because in C# every function must live inside a class. When someone says "function," they usually mean a method that doesn't need an object to run (a static one — more in §4). Don't overthink the distinction; interviewers won't grill you on it.

4. static vs instance — the distinction that unlocks everything

This one word decides whether you need an object or not.

Instance member

belongs to a specific object

You must new one up first, then call it on that object. Each object has its own data.

var tier = new DoseTier();
tier.DoseMg = 150;   // this tier's dose

static member

belongs to the class itself

No object needed. Call it straight on the type name. Great for stateless helpers & constants.

PlannerCalculator.IntervalDays(plan);
// PlannerCalculator = class (static).
// plan = an object we pass in.
// never "new PlannerCalculator()"

In your app

Your whole PlannerCalculator is a static class — it's pure math with no data to remember, so it never needs to be instantiated. Compare:

public static class PlannerCalculator   // ← static class = "just a toolbox of functions"
{
    public static double IntervalDays(PeptidePlan plan)  // call as PlannerCalculator.IntervalDays(...)
    {
        return plan.ScheduleMode == ScheduleModes.Interval
            ? Math.Max(1, plan.EveryDays)
            : 7 / Math.Max(0.1, plan.ShotsPerWeek);
    }
}
In plain English "This is a toolbox, not a thing you own — you never build one. Ask it: for this plan, how many days between shots? If the plan uses interval mode, use its EveryDays (but never less than 1). Otherwise, split 7 days across the shots-per-week."

Meanwhile PeptidePlan is a normal (non-static) class, because every plan carries its own peptide name, dose, dates — data that must live in an object.

Rule of thumb: Does this thing need to remember data unique to it? → instance class. Is it just a reusable calculation or constant? → static.

5. Properties: the { get; set; } mystery

Why not just write public double DoseMg;? Here's the deal.

A property looks like a field (a variable) but is secretly a pair of tiny methods: a get (the code that runs when you read it) and a set (the code that runs when you write it). { get; set; } is C# saying "generate the obvious read/write for me." You use it like a plain variable, and the hidden methods fire automatically:

plan.DoseMg = 150;        // you're WRITING → the `set` runs (the value 150 arrives as `value`)
double d = plan.DoseMg;   // you're READING → the `get` runs and hands back the stored value

What get and set literally are

When you write the short form { get; set; }, the compiler secretly writes this longer version for you — a hidden storage slot ("backing field") plus two methods:

// This short line…
public double DoseMg { get; set; }

// …is shorthand for roughly THIS:
private double _doseMg;                       // hidden variable that actually holds the value
public double DoseMg
{
    get { return _doseMg; }               // runs when someone READS DoseMg
    set { _doseMg = value; }             // runs when someone WRITES DoseMg
}
In plain English "Keep the real number hidden in a private box called _doseMg. When anyone asks to read DoseMg, hand them what's in the box. When anyone assigns to DoseMg, drop the new value (value) into the box."

Inside a set, the special keyword value is "the thing on the right-hand side of the =." So in plan.DoseMg = 150;, value is 150. You never declare value — C# hands it to you automatically.

Why properties instead of plain variables?

Because a property is really methods in disguise, you can add logic later without changing any code that uses it. Say you want doses to never go negative — you just teach the set to guard, and every existing plan.DoseMg = … in the app is instantly protected:

private double _doseMg;
public double DoseMg
{
    get => _doseMg;
    set => _doseMg = Math.Max(0, value);   // clamp: negatives become 0 on the way in
}

That's the whole reason C# people default to { get; set; } over a bare field: it's a plain variable today, but leaves a door open to add validation, logging, or change notifications tomorrow — with zero edits to callers.

The variations you'll actually meet

Written asMeaning
{ get; set; }Read and write freely. (Your default.)
{ get; }Read-only — can only be set once, when the object is created. Great for values that shouldn't change afterward.
{ get; private set; }Anyone can read it; only this class can change it. Controlled write access.
{ get; init; }Settable only during object creation (new X { … }), then locked.
=> someExpression;Getter-only, computed on the fly. No stored value at all (see below).
= 100; after itA default value used if nobody sets one.

In your app — a "computed" property: getter only, no stored value:

Models.cs → PlannerStore
[JsonIgnore]
public PeptidePlan? ActivePlan => Plans.FirstOrDefault(p => p.Id == ActivePlanId) ?? Plans.FirstOrDefault();
In plain English "Whenever someone reads ActivePlan, look through my plans for the one whose Id matches ActivePlanId. If I find it, that's the answer. If none matches, just fall back to the first plan I have."

There's no set and no backing field here. ActivePlan stores nothing — every time you read it, the code after => runs fresh and finds the matching plan. Think of it as a getter whose body is "go compute the answer right now." It behaves like a read-only property but is really a live calculation. (The [JsonIgnore] on top is an attribute — metadata that tells the JSON serializer "don't include this in the output," since it's derived, not real data.)

6. Methods in depth

Reading a method signature is 80% of reading C#. Let's make it automatic.

public  static  int  TierDoseCount(DoseTier tier, PeptidePlan plan)
  ▲       ▲      ▲       ▲              ▲                    ▲
  │       │      │       │              └────────────────────┴─ PARAMETERS (inputs, each has a type + name)
  │       │      │       └─ method NAME
  │       │      └───────── RETURN TYPE: it hands back an int. ("void" = returns nothing.)
  │       └──────────────── static: call on the class, no object needed
  └──────────────────────── public: callable from anywhere

To call it: int n = PlannerCalculator.TierDoseCount(myTier, myPlan); — you pass a value for each parameter, and catch what it returns.

Two ways to write a method body

// Block body — for multi-step logic (uses { } and return):
public static double DosesPerWeek(PeptidePlan plan)
{
    return plan.ScheduleMode == ScheduleModes.Interval
        ? 7 / Math.Max(1, plan.EveryDays)
        : Math.Max(0.1, plan.ShotsPerWeek);
}

// Expression body — for one-liners. `=>` replaces { return … }. Same thing, shorter:
public Task<PlannerStore> GetStoreAsync() => repository.LoadCurrentAsync();

The ? : ternary — a compact if/else that produces a value

"Ternary" just means "an operator that takes three parts" (tri = three). It's a one-line way to choose between two values. The shape is always:

condition  ?  valueIfTrue  :  valueIfFalse

Read it out loud as a question: "Is the condition true? If yes, use this; otherwise, use that." It's identical to JavaScript's ternary, so you already know it.

The key difference from a normal if: an if statement does something (runs code); a ternary is a value you can assign or return. These two are equivalent:

// Plain if/else — 6 lines, assigns to a variable declared above:
double days;
if (plan.ScheduleMode == ScheduleModes.Interval)
    days = Math.Max(1, plan.EveryDays);
else
    days = 7 / Math.Max(0.1, plan.ShotsPerWeek);

// Same logic as a ternary — the whole thing IS the value, so you can return it directly:
return plan.ScheduleMode == ScheduleModes.Interval
    ? Math.Max(1, plan.EveryDays)          // used when the condition is TRUE
    : 7 / Math.Max(0.1, plan.ShotsPerWeek); // used when the condition is FALSE

In your app — PlannerCalculator leans on ternaries because almost every calc is "interval mode vs weekly mode." One from ScheduleLabel:

return plan.ScheduleMode == ScheduleModes.Interval
    ? $"every {plan.EveryDays} days"            // TRUE  → interval wording
    : $"{Formatters.Number(plan.ShotsPerWeek, 1)}x per week"; // FALSE → weekly wording

(The $"…{x}…" is an interpolated string — like a JS template literal `…${x}…`. The $ enables the { } slots.)

When to use it: reach for a ternary when you're picking between two values in a single line. If either branch needs to do several steps, use a full if/else — cramming logic into a ternary gets unreadable fast. And don't nest them deeply; one level is friendly, three is a puzzle.

7. record vs class

You used both. Here's when each makes sense.

A record is a class optimized for holding data that doesn't change — think "a message that just carries values." It gives you a super-compact syntax and value-based equality for free.

In your app — the shapes of incoming API request bodies:

Api/PlannerEndpoints.cs
public sealed record TierCreate(string? Type, double Weeks = 1, int Count = 1, double DoseMg = 0);
In plain English "Make me a little data-holder called TierCreate with four slots — Type, Weeks, Count, DoseMg. If the caller doesn't give Weeks/Count/DoseMg, default them to 1, 1, and 0. Once built, it doesn't change."

That single line declares a type with four read-only properties and a constructor to fill them. The equivalent class would be ~15 lines. When the browser POSTs JSON, .NET builds one of these TierCreate objects and hands it to your endpoint.

classrecord
Use forThings with changing state & behavior (PeptidePlan)Immutable data carriers (API DTOs like PlanUpdate)
EqualityBy identity (same object in memory?)By value (same field values? → equal)
SyntaxVerboseOne-liner positional form

"DTO" = Data Transfer Object — a dumb bag of fields whose only job is to move data across a boundary (browser → server). Good interview vocabulary.

8. Nullable types & null-safety

The ?, ??, and is null you keep seeing.

C# forces you to be explicit about "this might be missing." A ? after a type means "or null":

SyntaxMeansYour code
int?an int, or null (value not provided)int? PreviewCount in PrefsUpdate
PeptidePlan?a plan, or null (maybe none found)ActivePlan

In your app — the PUT /prefs handler only updates fields the client actually sent:

if (body.PreviewCount is { } pc) prefs.PreviewCount = pc;  // pc = the non-null value
if (body.MaxUnits is { } mu) prefs.MaxUnits = mu;
In plain English "Did the caller actually send a PreviewCount? If yes, call that value pc and save it. Same for MaxUnits. If a field came in as null (not sent), leave the existing setting untouched."

Because each property is nullable (int?, double?), "not sent" (null) is distinguishable from "sent as 0". That's why partial updates work correctly.

Why C# nags you about null: the #1 crash in most programs is "tried to use something that was null." C#'s nullable rules push those bugs to compile time, so your app doesn't blow up on a user. In an interview, calling this out shows maturity.

9. Collections & LINQ

LINQ is C#'s .map/.filter/.find — you'll recognize it instantly.

JavaScriptC# LINQDoes
arr.find(p => …)list.FirstOrDefault(p => …)first match, or null if none
arr.filter(p => …)list.Where(p => …)keep matches
arr.map(x => …)list.Select(x => …)transform each

That p => … is a lambda — an inline anonymous function, exactly like an arrow function in JS.

In your app — straight from PlannerEndpoints.cs:

// find one plan by id (or null):
var plan = store.Plans.FirstOrDefault(p => p.Id == id);

// keep every plan EXCEPT the one being deleted:
store.Plans = store.Plans.Where(p => p.Id != id).ToList();

// dedupe + sort the manually-opened BAC dates:
prefs.ManualBacOpenDates = dates.Distinct().Order().ToList();
In plain English "Line 1: hunt through the plans for the first one whose Id matches — or nothing. Line 2: keep every plan except the one being deleted, and rebuild the list from what's left. Line 3: take the dates, throw out duplicates, sort them, and turn the result back into a list."

Call out every moving part

var plan = store.Plans.FirstOrDefault(p => p.Id == id);

  • var = C# figures out the variable's type from the right side. Here it becomes PeptidePlan?: a plan, or null.
  • plan = a new local variable. It will hold the matching plan object, or null.
  • store = an object. Specifically, the current PlannerStore object holding app state.
  • Plans = a property on store. It is the list of saved PeptidePlan objects.
  • FirstOrDefault(...) = a LINQ method/function call on the list. It returns the first item that matches, or the default value if none match.
  • p => ... = a lambda: a tiny inline function. Read it as "for each plan, call that plan p, then check..."
  • p = one plan object from store.Plans while LINQ is checking the list.
  • p.Id = the Id property on that one plan object.
  • id = the id value we are looking for, usually from the URL route like /plans/{id}.
  • == = comparison operator. It asks "are these two values equal?"

Read the line as: "Make a variable named plan. Search the store's Plans list. For each plan p, check whether p.Id equals the requested id. Give me the first match, or null."

store.Plans = store.Plans.Where(p => p.Id != id).ToList();

  • store.Plans = ... = replace the old Plans list with a new list.
  • store = the same PlannerStore object.
  • Plans = the list property being read on the right side and overwritten on the left side.
  • Where(...) = a LINQ method/function call like JavaScript filter. It keeps only items where the condition is true.
  • p => p.Id != id = lambda saying "for each plan p, keep it if its Id is not the deleted id."
  • p = one plan object currently being tested.
  • p.Id = the id property on that one plan.
  • != = not-equal operator. It asks "are these two values different?"
  • ToList() = method/function call that runs the LINQ query and turns the result back into a real List<PeptidePlan>.

Read the line as: "Build a new Plans list containing every plan except the one whose Id matches id, then save that new list back onto store.Plans."

prefs.ManualBacOpenDates = dates.Distinct().Order().ToList();

  • prefs = an object holding user preferences/settings.
  • ManualBacOpenDates = a property on prefs. It stores the manually opened BAC water dates.
  • dates = a local variable holding the incoming date values.
  • Distinct() = LINQ method/function call that removes duplicates.
  • Order() = LINQ method/function call that sorts the remaining dates.
  • ToList() = method/function call that turns the sorted result into a real list.
  • The dots mean chaining: take the result from one method and immediately call the next method on it.

Read the line as: "Take the incoming dates, remove duplicates, sort them, convert them to a list, then store that clean list in prefs.ManualBacOpenDates."

Why .ToList() at the end? LINQ is lazy — Where just describes a query; nothing runs until you force it. .ToList() runs it and freezes the results into a real list. (Not always needed, but common.)

10. async / await / Task

Same idea as JavaScript's async/await — but Task deserves a real deep-dive, because it's the piece people wave past.

First, the quick JS map

JavaScriptC#
PromiseTask (finishes, no result) / Task<T> (finishes with a value of type T)
async function f()async Task<T> F()
await g()await G()

So what is a Task, really?

A Task is an object that represents a piece of work that may not be finished yet. It's a receipt, an IOU, a "I'll get back to you." When you start slow work (reading SQLite, calling a network), you don't get the answer immediately — you get a Task handle right now that promises to hold the answer later.

Analogy: you order coffee and get a buzzer. The buzzer isn't the coffee — it's a stand-in you can hold, put in your pocket, or hand to a friend. When the coffee's ready the buzzer goes off. A Task is that buzzer; await is "sit and wait for it to buzz, but let other people order while I wait."

Every Task is in one of a few states, and it moves through them:

StateMeaning
Running (not completed)The work is still in progress. The buzzer hasn't gone off.
RanToCompletionFinished successfully. If it's a Task<T>, the result value is now sitting inside it.
FaultedThe work threw an exception. await-ing it will re-throw that exception to you.
CanceledIt was cancelled before finishing (via a cancellation token).

Task vs Task<T> — the one distinction to nail

Task

work that finishes, but hands back nothing

Like a void method, but async. You await it just to know "it's done."

await repository.SaveCurrentAsync(store);
// nothing to capture — we just wait for the write to finish

Task<T>

work that finishes AND produces a value of type T

await unwraps it and gives you the T inside.

PlannerStore store = await repository.LoadCurrentAsync();
// LoadCurrentAsync returns Task<PlannerStore>;
// await peels off the Task<> wrapper → a PlannerStore

The mental model for await: it "unwraps" the box. await a Task<PlannerStore> and you get a PlannerStore. await a plain Task and you get nothing (like unwrapping an empty box) — you just move on knowing it's done. Forgetting the await is the classic bug: you'd be holding the buzzer and trying to drink it, instead of the coffee.

Reading an async method signature

public  async  Task<PlannerStore>  LoadCurrentAsync()
  ▲       ▲            ▲                    ▲
  │       │            │                    └─ note the "Async" name suffix — a convention, not a rule
  │       │            └─ RETURN TYPE: "eventually gives back a PlannerStore"
  │       └───────────── async: "this method uses await inside, and hands back a Task"
  └───────────────────── normal access modifier

Key insight: the method is declared to return Task<PlannerStore>, but inside its body you return a plain PlannerStore. The async keyword tells the compiler to automatically wrap your return value in a Task for you. You write "return the store"; the caller receives "a Task that will contain the store."

Why bother? What await actually buys you

When your server hits await repository.LoadCurrentAsync(), reading from disk takes (in computer terms) ages. Two ways to handle that wait:

Blocking (bad)Async with await (good)
The threadSits frozen, doing nothing, until the disk replies.Is released back to the server to go handle other requests.
Under load100 slow requests = 100 stuck threads = server chokes.A handful of threads juggle thousands of waiting requests.
When done—The runtime grabs a free thread and resumes right after the await, as if it never paused.

So await means "pause this logical flow, but don't waste the thread — go be useful elsewhere, and wake me up when my Task completes." That's the whole point of async on a web server: throughput.

In your app — PlannerService.MutateAsync, now annotated for Tasks:

// Declared to return Task<T>. `async` lets us use `await` inside and auto-wraps the result.
public async Task<T> MutateAsync<T>(Func<PlannerStore, T> mutate)
{
    await _gate.WaitAsync();                      // await a plain Task → just "wait until I hold the lock"
    try
    {
        PlannerStore store = await repository.LoadCurrentAsync(); // await Task<PlannerStore> → unwrap to a PlannerStore
        T result = mutate(store);              // synchronous (fast) — no Task, no await needed
        PlannerNormalizer.Normalize(store);
        await repository.SaveCurrentAsync(store);      // await a plain Task → wait for the write to finish
        return result;                          // we return a T; caller receives Task<T> (async wraps it)
    }
    finally { _gate.Release(); }                  // runs no matter what, even on exception
}
In plain English "Wait my turn for the lock so no one else touches the data at the same time. Once I have it: load the current state from the database, run whatever change was handed to me, tidy it up, and save it back. Give the caller back whatever the change produced. And no matter what happens — success or crash — always let go of the lock on my way out."

Notice the mix: some calls are await-ed (the slow, Task-returning ones — lock, DB read, DB write) and some aren't (mutate and Normalize are fast, synchronous, return no Task). You only await things that hand you a Task.

Two rules people trip on

  1. To await, your method must be async. The two travel together: if any line inside uses await, the method's signature needs async and must return Task / Task<T> (a top-level app entry point can be an exception).
  2. await unwraps and re-throws. If the awaited Task faulted, the exception surfaces right at the await — so ordinary try/catch works around async calls, exactly like synchronous code. That's how your Run(...) helper in §12 catches a PlannerApiException thrown deep inside an awaited mutate.
Bonus: running Tasks in parallel with Task.WhenAll

Because a Task is just a handle, you can start several without awaiting immediately, then wait for all of them together — they overlap instead of running one-after-another:

// Kick both off — no await yet, so they run concurrently:
Task<ComputedPlan> a = svc.ComputeAsync(planA);
Task<ComputedPlan> b = svc.ComputeAsync(planB);

// Now wait for both to finish:
ComputedPlan[] results = await Task.WhenAll(a, b);

This is C#'s Promise.all([...]). Your app doesn't need it today (its DB work is serialized behind a lock on purpose), but it's a common interview follow-up: "how would you run these two independent async calls at the same time?" → Task.WhenAll.

11. Dependency Injection (DI)

The "how do my classes get their collaborators" pattern that's everywhere in .NET.

Instead of a class building its own dependencies, it declares what it needs in its constructor, and .NET hands them over. This is DI. It sounds fancy; it's just "don't new your own stuff — ask for it."

Services/PlannerService.cs
public sealed class PlannerService(PlannerRepository repository)
                                    ▲
   "I need a PlannerRepository to do my job. Someone please give me one." ┘

Who provides it? You registered the wiring once, at startup:

Program.cs
builder.Services.AddSingleton<PlannerRepository>();  // "make ONE, share it everywhere"
builder.Services.AddSingleton<PlannerService>();     // PlannerService auto-gets the repository above
In plain English "Hey .NET: for the whole life of this app, keep exactly one PlannerRepository and one PlannerService around. Whenever anybody asks for either, hand them that same shared instance — and when you build the PlannerService, you already know it needs a PlannerRepository, so plug it in for me."

Now anywhere that needs a PlannerService — like your API endpoints — just lists it as a parameter and .NET supplies the fully-built instance:

api.MapGet("/state", async (PlannerService svc) => Results.Ok(await svc.GetStoreAsync()));
                                     ▲ .NET injects the shared PlannerService here, automatically

Why bother? (Great interview answer.) It keeps classes loosely coupled and makes them testable — in a unit test you can inject a fake repository. AddSingleton = one shared instance for the app's life; other flavors are AddScoped (one per web request) and AddTransient (a fresh one every time).

12. The API & a request's journey

Your API uses ASP.NET "Minimal APIs" — routes declared as one-liners. Let's trace one end-to-end.

Your PlannerEndpoints.MapPlannerApi() registers the whole REST surface. A sample:

Api/PlannerEndpoints.cs
var api = app.MapGroup("/api");                // every route below is prefixed with /api

api.MapGet("/plans", …);                    // GET  /api/plans        → list plans
api.MapPost("/plans", …);                   // POST /api/plans        → add a plan
api.MapPut("/plans/{id}", …);              // PUT  /api/plans/abc    → update plan abc
api.MapDelete("/plans/{id}", …);           // DELETE /api/plans/abc  → remove plan abc
api.MapGet("/plans/{id}/compute", …);      // GET → full vial math for one plan
api.MapGet("/schedule.ics", …);            // GET → downloadable calendar file
In plain English "Set up a group of routes all starting with /api. When a GET request comes in for /api/plans, run this handler. When a POST comes to /api/plans, run that one. The {id} in the path is a fill-in-the-blank — whatever's there gets handed to the handler as id."

What happens when the browser calls POST /api/plans/abc/tiers

Step through the whole request
  1. Route match. ASP.NET sees the URL + verb and picks MapPost("/plans/{id}/tiers", …). It pulls id = "abc" out of the URL.
  2. Model binding. The JSON body is deserialized into a TierCreate record. PlannerService is injected (§11).
  3. Your handler runs. It calls Run(svc, store => { … }), passing a lambda that adds the new tier to the right plan.
  4. Atomic mutate. Run → svc.MutateAsync(…) locks, loads state from SQLite, applies your lambda, normalizes, saves. (§10)
  5. Result → HTTP. Success returns Results.Created(...) → HTTP 201. A PlannerApiException becomes Results.Problem(...) → 404/409. .NET serializes the object back to JSON.

In your app — the error-to-HTTP translation, one tidy helper:

private static async Task<IResult> Run<T>(PlannerService svc, Func<PlannerStore, T> mutate, bool created = false)
{
    try
    {
        var result = await svc.MutateAsync(mutate);
        return created ? Results.Created(…, result) : Results.Ok(result);
    }
    catch (PlannerApiException ex)
    {
        return Results.Problem(detail: ex.Message, statusCode: ex.StatusCode);
    }
}
In plain English "Try to apply the change to the store. If it works, reply 201 Created (for new things) or 200 OK (otherwise) with the result. But if the change threw one of our known errors — like 'no plan with that id' — don't crash; catch it and reply with that error's own status code and message instead."

IEndpointRouteBuilder, IResult, IConfiguration — the leading I is a naming convention for interfaces: a contract listing methods a type promises to provide, without saying how. Your code depends on the contract, not a specific implementation — that's what makes swapping/testing possible.

13. Trouble spots, nailed ★

The six things you told me still feel fuzzy — each boiled down to a sentence you can repeat, plus a quick gut-check.

① Class vs Object vs Method (the one to over-learn)

Say this out loud until it's boring:

Class = the recipe. Object = the cake you baked from it. Method = something the cake can do ("slice yourself").

Gut-check with your own code — which is which?

var plan = new PeptidePlan();     // PeptidePlan = class (recipe).  plan = object (the cake).
plan.Tiers.Add(new DoseTier());  // Add = method (an action the Tiers object performs).
In plain English "PeptidePlan is a template describing what a plan is. new bakes one real plan and I name it plan. Then I tell that plan's tier-list to do something: add a fresh tier."

Fastest tell: if you can type .something() after it and it does a thing, that's a method. If you wrote new X, the result is an object. The bare word X after class is the class.

② new vs static — a 2-question decision

This is the same confusion wearing a different hat. Ask yourself:

QuestionIf YESIf NO
Does this thing need to remember data unique to it (its own name, dose, dates)?It's an instance → you must new one.Maybe static…
Is it just a calculation/helper with no memory of its own?static → call it on the type, no new.Instance.
PeptidePlan plan = new();          // NEW: each plan carries its own data → instance
double d = PlannerCalculator.IntervalDays(plan);  // STATIC: pure math, no data of its own
double m = Math.Max(1, x);         // STATIC: Math is a toolbox — you never "new Math()"
In plain English "If every copy would hold different information, I need to build individual copies with new. If it's just a reusable tool that takes inputs and gives an answer, it can be static — one shared toolbox, no building required."

One-liner for the interview: "Instance members hold per-object state; static members belong to the type and are for stateless helpers or shared constants."

③ get / set — what actually happens

A property is a variable with two tiny hidden methods bolted on. Reading runs the get; assigning runs the set (where value = the thing you assigned).

plan.VialMg = 500;      // runs the SET  → value is 500
var v = plan.VialMg;    // runs the GET  → hands back 500
In plain English "It looks like a plain variable, but under the hood, reading it calls a little 'give me the value' function and writing it calls a little 'store this value' function. That's why I can add rules later without changing callers."

Why anyone cares (say this): "Auto-properties look like fields but are methods, so I can later add validation, make the setter private, or compute the value — without touching any calling code."

④ Dependency Injection — the one-sentence version

"A class asks for what it needs in its constructor, and the framework hands it over — instead of the class building its own dependencies."

public sealed class PlannerService(PlannerRepository repository) { … }
                                    ▲ "give me a repository; I won't make my own"
In plain English "PlannerService doesn't go find or build a database repository itself. It just says 'I need one of these,' and at startup I told .NET how to supply it. .NET wires them together for me."

Why bother (the payoff line): "It decouples classes from their dependencies, so I can swap implementations and inject fakes in tests." Lifetimes: Singleton (one forever), Scoped (one per web request), Transient (a new one every time).

⑤ sealed — and the inheritance idea behind it

To get sealed, you need one background idea: inheritance. Normally a class can be used as a base that other classes extend (inherit its members and add/override). sealed slams that door: "no one may inherit from this class."

public sealed class DoseTier { … }   // nobody can write ": DoseTier" to extend it
In plain English "This class is finished. You can use it and create objects from it, but you can't make a specialized subclass of it. It's locked as-is."

Why nearly every class in your app is sealed (great answer): "These are data models and services with no intent to be subclassed. Sealing states that intent, prevents accidental inheritance, and even lets the runtime optimize method calls. It's a sensible default unless you're deliberately designing for extension."

⑥ Task / async / await — the 20-second recap

ThingSay this
Task"A handle to work that isn't done yet — a buzzer/IOU. Task<T> also carries a result of type T."
await"Pause this flow until the Task finishes and unwrap its result — but free the thread to do other work meanwhile."
async"Marks a method that uses await inside and returns a Task."
In plain English "Slow work hands me a buzzer instead of making me stand frozen at the counter. await means 'go help other customers, and tap me when this buzzer goes off — then give me my coffee.'"

Why it matters on a server (the point): "It's about throughput. While one request waits on the database, the thread is freed to serve others, so a few threads handle thousands of overlapping requests."

If they ask "what confused you learning C#?" — turn it into a strength: "Coming from JS, the biggest shift was that C# is strongly typed and compiled, so a lot of my old runtime bugs now surface at compile time. Getting comfortable with types, Task<T>, and dependency injection was the learning curve — and I appreciate the safety they buy." Honest + shows growth.
